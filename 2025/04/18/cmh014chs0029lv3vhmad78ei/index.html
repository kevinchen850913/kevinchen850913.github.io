COM Port 隨便寫真的沒問題嗎?

發表於2025-04-19|更新於2025-10-21

某天下午，一位工程師同事來找我求助。他在測試一個裝置連線流程時，應用程式莫名當掉。最初看起來像是硬體或驅動的問題，但這次的錯誤行為特別難以重現，狀況也特別詭異。插上特定的 USB 裝置後，畫面凍結，整個 UI 無反應，也沒有任何錯誤訊息。

他已經追查過幾個方向但沒有頭緒，於是我加入了這場 Debug 任務。

第一步是觀察異常觸發條件，這已經讓我高度懷疑是 COM Port 掃描過程出問題，尤其是掃描邏輯中沒有針對裝置型態做過濾，極可能碰到了某些系統不該碰的裝置。

  • 如果裝置透過藍牙連線，應用程式就會在插入時卡住。
  • 如果是一般 USB 裝置，則沒有這個問題。
  • 一定要「先開啟應用程式，再插裝置」才會發生。

我們開始查原始碼，發現 COM Port 掃描邏輯大致如下

這段程式碼是同步執行的，而且直接放在 UI 執行緒上。如果這段 .Get () 在查詢過程中遇到某個裝置出現卡頓（例如藍牙 COM Port 的假裝置），整個主執行緒就會被鎖死，導致 UI 無反應。

這也解釋了為什麼錯誤沒有訊息、為什麼 UI 卡住而不是崩潰：因為主執行緒被同步呼叫卡住了。

# 白名單過濾裝置

為了快速讓軟體恢復正常，我先加上一層裝置過濾，只讓明確支援的 FTDI 類型進入後續邏輯。解決方案，確認裝置 DeviceID 中必須包含 “FTDIBUS”。

這段簡單的條件式排除了所有非 FTDI 的裝置，其中也包含那些會造成卡頓的藍牙 COM Port。這讓當機問題立即獲得緩解。

# 拔插仍會異常

雖然掃描不再卡住，但後續測試時，我們還是發現裝置插拔時有機率拋出 Runtime 錯誤。出現 WMI 查詢物件在 COM 上下文中已經無效時仍被呼叫導致的錯誤，通常發生在非同步操作未清除物件、或物件生命週期被錯誤管理的情況。

發現設計問題，太多地方在重複掃 COM Port，整個專案中有多段重複的 COM 掃描邏輯，例如：

  • 開啟視窗時自動掃描一次
  • 按某個按鈕會再次掃描
  • 背景執行緒會定時掃描
  • WndProc 裡偵測裝置插拔後再掃一次

最糟的是，這些地方使用的是不同版本的 GetCOMList ()，過濾條件也不一致。也就是說，有的地方會掃到藍牙 COM，有的沒過濾，有的開 Port 有做檢查，有的沒有。

這會導致異常無法穩定重現，而且很難追蹤哪段邏輯導致崩潰。

# 限制刷新條件

軟體異常可能與寫法有關，有些功能直接在 WndProc 上執行， 如果該功能需要等待時間，軟體會變得比較不穩定，會受到電腦速度影響。

測試時發現的現象，當分頁切換至 Display 時會開啟 USB，導致 WndProc 被多次觸發。我們最終決定將所有 Port 掃描邏輯集中成一個方法 GetValidCOMList ()，統一過濾與操作流程。

這次順勢清除了幾個無人維護的功能，例如 COMListCheck ()，幾年來沒人知道它到底做什麼。我們也把部分直接寫在 WndProc 裡的延遲操作改為非同步，避免 UI thread 遭到阻塞。
