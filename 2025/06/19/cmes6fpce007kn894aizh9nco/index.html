資安 CRA 準備與檢討筆記

發表於2025-06-20|更新於2025-08-26

最近在準備 CRA（Cyber Resilience Act，歐盟網路韌性法案）相關的資安合規時，發現這已經不只是「多寫幾份文件」這麼簡單的事。

CRA 其實等於是把整個產品開發流程拉進資安架構裡，從設計圖第一筆畫下去那刻起，你就得開始想「資安怎麼做」。這邊整理幾個我們自己在準備過程中覺得很有感的觀察，也當作未來檢討用。

# 資安不再是加值功能

以前做產品，資安常常被當成「之後再補」的選項。但現在 CRA 的邏輯很明確：一開始就要設計安全，預設就要安全（Security by Design & Default）。不然就不是一個可以進市場的產品。

幾個實際要落地的地方：

  • 開發流程要納入 SDL（安全開發生命週期），這不是貼一張流程圖而已，而是每個人都要知道自己哪個階段該處理哪些資安問題。
  • 產品預設值就要是安全的。不是「讓用戶去改密碼」那種安全，是即使他什麼都不改，也要能抵擋基本攻擊。
  • 這些改動意味著：開發成本確實上升，但相對的，能提早發現問題，少掉一堆事後補洞的災難場面。

CRA 上市前要通過所謂的「Conformity Assessment」，簡單講就是你要能證明自己的產品是安全的。有些產品可以自己評估，有些（例如路由器、VPN 軟體）則一定得經過第三方認證。

我們實際碰到的狀況包括，文件量暴增（風險評估、設計說明、更新流程、用戶說明書……），上市時程被拉長，不只是 QA，要多塞一段合規流程，有些產品還得新增角色處理 CRA 的相關事務，不能混在 PM 或 RD 的工作裡當 side project。

# 實作上的幾個對策

# USB 更新變成地雷

問題：透過 USB 更新很方便，但也最容易被當成入侵管道。

我們的做法，所有更新檔都要用 RSA 簽章 + SHA-256 驗證，裝置內建公鑰來驗真偽。USB 更新只能在維修模式下進行，防止用戶誤觸或惡意觸發。只有經授權的 USB 裝置能啟用更新（用內建金鑰或認證碼做識別）。

文件類型 說明
軟體更新架構說明 包含驗證流程、簽章與金鑰管理
資安風險分析（如 STRIDE、DREAD） 包含 USB 接口攻擊面分析
更新記錄與稽核設計 說明記錄方式與保存期限
使用者手冊 明確說明如何進行安全更新
資安支援週期公告 包含更新頻率、停止支援年限等

# 降級裝回漏洞版

問題：即使你現在修好了漏洞，駭客如果能降回舊版本，就可以重新利用。

我們的做法，禁止降級更新（rollback protection），版本號做硬性限制。所有歷史版本都要記錄，並做風險註解。若更新失敗，裝置會自動回復到最後穩定版本。

安裝更新時會暫停正常功能，防止中途關機造成磚頭（bricking）。整個更新流程設計有「安全回復」機制。所有更新資訊皆加密，避免洩漏用戶或裝置機密。

# 資安維護週期

品上市前須進行資安合規評估（Conformity Assessment），企業需自評或找第三方機構，確認產品符合資安要求，某些「關鍵類產品」可能需通過嚴格認證程序（例如路由器、VPN 軟體）

需公告支援期限與資安維護週期（Product Security Lifecycle），用戶應清楚知道產品資安支援會維持多久，過期產品需適當處置或有退場機制，產品設計與維運策略需透明化，避免舊產品成為資安漏洞入口。

# 重點是你要擋下來

CRA 的邏輯很直接 —— 如果你設計的更新流程最後沒能擋下未授權更新，那就是你的錯。不是「駭客太強」，是你沒設好門。就像銀行設了雙重驗證，但資料庫後門沒鎖，客戶用到也不能推給他「點錯連結」：責任在你。

金鑰保護：不只是私鑰，連公鑰都不能亂丟

類型 CRA 可能怎麼看
公鑰被反編譯 如果你沒用加密、白盒設計、安全區保存，那就是疏忽
私鑰外洩 極嚴重，視為製造商失責
金鑰放在 GitHub 或忘在 USB 可追責，屬人為可預防錯誤
Debug 模式能讀出金鑰 若沒混淆、封裝等保護，也視為設計漏洞

這整個 CRA 準備過程，讓我們體認到，資安設計不能再被當成附加項目，它得內嵌在產品架構裡，合規≠形式過關，而是實質上擋得住攻擊，透明與可預測性會成為產品競爭力：用戶會看你支援多久、怎麼處理漏洞，雖然整體來看，開發、上市流程的確變得更重了，但能把這些事提早做、做對，反而能在市場上少很多「回收危機」與「信任損耗」。
