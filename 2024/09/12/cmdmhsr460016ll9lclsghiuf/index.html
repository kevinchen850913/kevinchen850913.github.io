# Platform Firmware Resiliency (PFR)

在 2017 年有個病毒 BrickerBot，他是透過網路刷機將 IoT 設備上的韌體變成磚頭 (Brick)，這種攻擊手法被稱為 PDoS (Permanent denial-of-service attacks /phlashing)，和 DDoS 讓服務器暫時癱瘓的攻擊手法相比，這是永久性的讓硬件癱瘓，必須重新更新才能復原。

隔年 (2018) 美國國家標準暨技術研究院 (NIST) 發布了 NIST SP 800 193 標準 (Platform Firmware Resiliency Guidelines)，裡面提及 Platform 上的 Firmware 應該要符合的安全措施。

# NIST Special Publication 800-193

PFR : Platform Firmware Resiliency Guidelines (NIST Special Publication 800-193) 是 NIST 提出的一種規範。

Platform Firmware Resiliency Guidelines 提供支援平台抵禦潛在破壞性攻擊的彈性的技術指南。 這些指南基於以下三個原則 :

  • Protection：確保平台韌體程式碼和關鍵資料保持完整性狀態並防止損壞的機制，例如確保韌體更新的真實性和完整性的過程。
  • Detection：用於偵測平台韌體程式碼和關鍵資料何時被損壞的機制。
  • Recovery：在偵測到任何此類韌體程式碼或關鍵資料已損壞或透過授權機制強制復原時，將平台韌體程式碼和關鍵資料還原為完整性狀態的機制。 恢復僅限於恢復韌體程式碼和關鍵資料的能力。

# Intel® PFR Overview

To provide resiliency by protecting platform assets against firmware attacks, detecting any corrupted firmware as well as malicious or erroneous behaviourand automatically restoring the corrupted firmware to recover the platform to a known good state.

保護平台資產免受韌體攻擊、檢測任何損壞的韌體及錯誤行為，並自動恢復損壞的韌體，將平台恢復到已知的良好狀態。

# PFR 規範筆記

Platform Architecture : 提供一些平台或軟體架構上的建議，建議硬體可以採用那些安全零件 (非為強制性)，建議韌體更新檔案要使用數位簽章，建議韌體不要將資料放在不安全的位置。

Principles and Key Concepts : 說明 Protection、Detection、Recovery 的流程該如何設計，並逐步帶入到 RoT 和 CoT 這兩項技術之中。

Firmware Security Guidelines for Platform Devices : 說明 RoT 、 CoT、RTU 、RTD、RTRec 等核心技術，並利用這些核心技術完成更加安全的執行 Protection、Detection、Recovery 功能。

# Root of Trust (Rot)

Root of Trust 指的是信任的源頭，RoT 是鏈中受信任的組件，並以安全的方式，將信任擴展到其他組件。

多數情況 RoT 是低階平台韌體的一部分，共享許多元件，通常 RoT 不會實現所有功能，錨定於 RoT 的 CoT 會協助實現。

非對稱式加密
非對稱式加密會有兩把對應的鑰使，私鑰可以產生公鑰，而公鑰則無法產出私鑰 (數學難題)，除此之外私鑰、公鑰並無差別。

  • 使用私鑰簽章，使用公鑰解密，功能是確保檔案為特定對象產生。
  • 使用公鑰簽章，使用私鑰解密，功能是確保檔案為特定對象解密。

# PFR 與 RoT 的關係

RoT 是 PFR 中的關鍵技術，但 PFR 規範並不僅限於此。

RoT 有多種實現方式 :

  • Hardware Root of Trust (HRoT) / Platform Root of Trust (PRoT)
  • HRoT : AST1060 的作法，信任源自於硬體。
  • PRoT : 偏向服務商的作法，信任源自於原廠的伺服器。

想像一下 : PFR (車輛安全規範文件)， Recovery (車禍時的安全機制)、 RoT (安全氣囊技術)

# Chain of Trust (CoT)

「信任鏈（Chain of Trust，CoT）」是一種在數位安全和認證過程中用來驗證身份和確保資料完整性的機制。它是基於一系列的信任關係，這些關係通常由數位證書和公鑰基礎設施（PKI）建立，並在該鏈中形成一個由一個受信任的根證書開始，逐層擴展到最終的證書或憑證。

簡單來說，信任鏈的概念就是從一個根證書（通常由受信任的證書機構或 CA 提供）出發，根證書簽發給子證書（例如中間證書），這些中間證書再簽發給終端證書。通過這樣的層級結構，終端證書的有效性和可信性可以由根證書確保，從而建立起信任。

# CoT 數位簽章應用

PRoT 如果簽章有任何狀況，只要向數位簽章服務商註銷，即可使公司數位簽章失效。

# ASPEED PFR (AST1060)

ASPEED PFR 是基於 AST1060 SOC 開發的整合硬體和韌體解決方案，它受到英特爾 PFR 2.0 HRoT 解決方案 / 規範的啟發，並依賴開源社群提供的開源產品。

# Hardware security module (HSM)

HSM 是 RoT 的一種解決方案，在資料保存、加密、解密的過程中若有安全漏洞，則後續的任何安全機制都會喪失其功能，所以這些流程可以使用專用硬體來實現，使其從根本上無法被更改，隨後藉此拓展信任範圍。

HSM 想要解決軟體方案中被低估的問題。

# Root of Trust for Recovery (RTRec)

這是 AST1060 的 Capsule 信任流程， Recovery、 Update 都是採用此機制驗證。CSK = Code signing key。

  1. Capsule 中的 Root Public Key 會確認 PFR Flash 中的 RootKey_Hash 是否相同。
  2. 使用 Root Public Key 將 Sign_CSK_RS 解密成 CSK Public Key
  3. 使用 CSK Public Key 將 Sign_B0_RS 解密成 Block0
  4. Block0 中的 PC_Hash 會確認 Packet Content 的 Hash 是否相同。

# Root of Trust for Update (RTU)

  • AST1060 的 Update 驗證機制與 Recovery 驗證機制有很多相似之處，差異為 Update 的 Capsule 是由外部提供檔案，而 Recovery 則會驗證內部的 Capsule 檔案 。
  • AST1060 Update 錨定於 Rot ，所以需要持有 Root Private Key 、 CSK Private Key 與 BMC 的相關權限，才能進行 Update 。
  • 雖然 Update 流程有方法可以移除金鑰 (Decommission Capsule)，但 PFR 文件中建議不要變更 RoT。

# Root of Trust for Detection (RTD)

AST1060 的 Detection 機制是使用 PFM 完成
PFM = Platform Firmware Manifest
PFM 是 Project Cerberus 中使用的驗證機制
Cerberus is a NIST 800-193 compliant hardware root-of-trust

PFM 的對稱金鑰由硬體生成，並且對每個控制器都是唯一的，且對稱密鑰不可匯出或讀取，該機制與 RootKey_Hash 無關。

PFM 是硬體加密韌體後儲存的清單，其過程完全由硬體執行，韌體不可讀寫加解密過程，只能取得硬體驗證的結果。

# AST1060 Provision Flow

AST1060 未 provision 時會直接啟動不檢查。

使用 BMC 或 BIOS 提供 AST1060 公鑰檔案的位置。

將 AST1060 上鎖，從此 BMC、BIOS 失去任何修改 AST1060 的能力。

如果客戶會自行上鎖 AST1060，那平台服務商就不需要取得金鑰，如果平台服務商協助上鎖，那就要取得客戶的公鑰，而且只有一次機會，AST1060 上鎖後，平台服務商就沒有方法可以改動，因為沒有私鑰，私鑰需要客戶自行妥善管理避免外流。
