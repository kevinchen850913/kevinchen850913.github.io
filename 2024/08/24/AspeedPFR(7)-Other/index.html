# Roots of Trust

信任的根源 Roots of Trust (RoT)
本節提供有關信任根 (RoT) 和信任鏈的基本準則 (CoT) 支援後續的保護、偵測和恢復指南。 這些指導方針是根據負責每個安全的邏輯組件來組織的。

  • 更新信任根 (RTU) 負責驗證韌體更新和關鍵資料變更以支援平台保護功能。
  • 偵測信任根 (RTD) 負責韌體和關鍵數據腐敗檢測能力。
  • 恢復信任根 (RTRec) 負責恢復韌體和偵測到損壞或管理員指示時的關鍵數據

General Information
1.1 Introduction
This manual provides the related technical information about the newly developed ASPEED Root of Trust Hardware Processor – AST1060. This document is intended for product planners, system designers, and software developers who are going to adopt or have adopted this device to support Platform Root of Trust

1.1 簡介
本手冊提供了新開發的 ASPEED Root of Trust 硬體的相關技術信息處理器 – AST1060。本文檔適用於產品規劃人員、系統設計人員及軟體開發人員採用或已採用該設備來支援平台信任根。

Chip Architecture
AST1060 is a Platform Root of Trust Processor introduced by ASPEED Technology Inc. It is able to do secure/authenticated boot and root of trust function. A Cortex-M4F is integrated.
Embedded security block: hash and crypto enginer for security boot and root of trust peforms detect,protect

AST1060 是 ASPEED Technology Inc. 推出的平台信任處理器。它能夠執行安全 / 經過身份驗證的啟動和信任根功能。 整合了 Cortex-M4F。嵌入式安全性區塊：用於安全啟動和信任根執行偵測、保護的雜湊和加密引擎並恢復功能。

# Zephyr 加密方案

Aspeed Zephyr 加密驅動程式實作了 hash、ecdsa 和 rsa 加密演算法。

數位簽章過程通常涉及三種演算法：

金鑰產生 – 此演算法提供私鑰及其對應的公鑰。
簽名 – 該演算法在收到私鑰和正在簽署的訊息後產生簽名。
驗證 – 此演算法透過驗證訊息以及簽名和公鑰來檢查訊息的真實性。
數位簽章的過程要求其附帶的公鑰可以驗證固定訊息和私鑰產生的簽章。使用這些加密演算法，如果無法存取其私鑰，則無法複製使用者的簽署。

The embedded security block provides the hash and crypto engine for secure boot and root of trust to perform Detect, Protect and Recover functions.

嵌入式安全性區塊提供雜湊和加密引擎，用於安全啟動和信任根，以執行偵測、保護和復原功能。

# BMC 如何產生並抽換對鑰

簽署 BMC 影像的流程

  1. 準備完整 256MB 的 BMC 活動鏡像
  2. 準備 OpenSSL 產生的金鑰對
  3. JSON 檔案定義韌體表現形式，包括 SPI 映像佈局、SMBus 或 I2C* 規則以及映像建置資訊
  4. 生成 PFM、簽署 PFM、將簽名的 PFM 加入 Active 鏡像中
  5. 建立 BMC 鏡像更新膠囊、簽署更新膠囊
  6. 將簽署的 BMC 更新膠囊加入到清單 JSON 檔案中定義的偏移位址處的完整 ROM 映像中

未來供客戶使用時會需要抽換金鑰，所謂的抽換金鑰就是步驟 2 中的準備 OpenSSL 產生的金鑰對，從配置檔案中換掉公私鑰，就可以影響簽核工具如何簽核與解密檔案。

Openssl 產生對鑰的流程，私鑰 ⇒ 公鑰，使用的加密為 secp384r1

產生私鑰的指令 openssl ecparam -name secp384r1 -genkey -out csk384_prv.pem

產生公鑰的指令 openssl ec -in csk384_prv.pem -pubout -out csk384_pub.pem

# Provision Flow

Both BIOS and BMC can provide the provision flow over the SMBus Host Mailbox. The Host Mailbox provides the UFM access registers which allow access to the UFM in order to write the provisioning data. The provisioning data include the Root Key Hash, CPU/BMC active PFM offset address in UFM, CPU/BMC Recovery region offset address in UFM and CPU/BMC staging region offset address in UFM.
After completing the provisioning of AST1060, trigger a reset which will trigger AST1060 authentication process with the newly provisioned data. On next boot, after verifying the system provisioning is complete and confirming status of ASPEED PFR, should send message to lock AST1060 UFM to protect the provisioned keys from any further modifications.

At initial state, the system is un-provisioned. System can boot up without any signature check and runtime protection.

第一次啟動時不用檢驗，啟動後用 SMBus 寫入配置，觸發重置，然後鎖上資料。

Aspeed 表示不解釋，自己看 Intel 文件，反正就是下這個指令。
3. Run aspeed pfr tool on BMC console: # aspeed-pfr-tool -b 4 -w 0x13 0x08
4. Please refer to Table 5.1 Host Mailbox Register File of Intel Platform Firmware Resilience Architecture and Hardware Design Guide (Reference Number: 606686) for the meaning of firmware update arguments.

我沒查到 Intel Platform Firmware Resilience Architecture and Hardware Design Guide，只有找到 784473_Intel Platform Security.pdf，不確定是否為同一份資料。

3.5.1 Authenticated Update Mechanism
An authenticated update mechanism employs digital signatures to ensure the authenticity of the
firmware update image. An update of the firmware image using an authenticated update
mechanism relies on a Root of Trust for Update (RTU) that contains a signature verification
algorithm and a key store that includes the public key needed to verify the signature on the
firmware update image. The key store and the signature verification algorithm are stored in a
protected fashion on the computer system and are modifiable only through use of an
authenticated update mechanism or a secure local update mechanism.

Intel 提供的更新含意，確實在使用更新包時會一並更新公鑰。

# mtd 跟 bin 的差異

參考 Image Difference between “.ext4” and “.mtd” files for bitbake

In summary, “.ext4” is more likely to be associated with the resulting image file containing an Ext4 filesystem, while “.mtd” might be relevant in the context of MTD partitions or flash memory management.

Bitbake 的「.ext4」和「.mtd」檔案之間的區別，「.ext4」更有可能與包含 Ext4 檔案系統的產生映像檔相關聯，而「.mtd」可能與 MTD 分割區或快閃記憶體管理的上下文相關。

.mtd MTD (Memory Technology Device) is a subsystem that manages flash memory devices.

“.mtd” might be used in the context of MTD partitions or flashing specific sections of memory

MTD_DEVICE = “your-flash-device”

MTD（Memory Technology Device）是管理快閃記憶體設備的子系統。「.mtd」可能用於 MTD 分區或快閃記憶體特定記憶體部分的上下文中

MTD_DEVICE = “您的快閃記憶體裝置”
檔案大小，mtd : 65536KB、bin : 36595KB
